bot-lab ハンドブック

打つコマンドは3つ。やってはいけないことは3つ。あなたの答えが要る質問が返ってくるのは2箇所。図を見れば分かるように書いてあります。

セットアップ（Python・gh・Claude Code を入れる手順）は、repo の ONBOARDING.md に全部書いてあります。claude と打って「コマンドが無い」と言われたら、このページではなくそちらへ。

今日やることだけ知りたいなら 「ひとりで最初の1時間」へ。手前の7節は、その前に知っておくと迷わない話です。

何をやっているか

応募フォームを自分たちで1つ作ります。これを的サーバと呼びます。そこへ大量の応募を撃ち、撃たれた側のログを自分で読む。片方しか持っていないと、bot 検知が何を見ているかは外から推測するしかありません。

あなたに頼むこと

頼むことは3つ。①Mac で動かす ②2台目のマシン（別の回線・別の観測点）になる ③「何を確かめたいか」を決める側に立つ——具体的には、完了条件つきの Issue を自分で立てるところまで（階段の3段目）。手を動かすのは Claude Code なので、エンジニアの経験は要りません。「動かなかった」は失敗ではなく成果です。

覚えなくていい3つ

拓也の環境設定は1ファイルも渡しません。拓也の OS と運用に張り付いていて、持って行った先では動かないからです。共有したいものは全部 repo の中にあります。

deny は、あなたがフォルダを「信頼する」より前から効きます。しかもあなたの手元の設定では緩められません——禁止が常に許可より優先される、と公式 docs が明記しています。

毎回の流れ

Issue を1つ選んで PR にする。この輪を繰り返します。

聞き返し①（/update）——まだ commit していない変更が手元にあると、上書きを避けて止まります。「変更を退避して続けて」と言えば進みます。Claude に「そんなコマンドは無い」と言われたら、「git pull してから」と伝えてください。

聞き返し②（/pr 3）——Issue に「何ができたら完了か」が無いと、実装に入らず質問を返します。答えられなければ、その質問ごと Issue #3 に貼って拓也へ。

PR に赤い ✗（CI が落ちた）が付いたら、同じ会話のまま Claude に「CI のログを読んで直して」と言えば直せます。直らなければ、その PR にコメントを1行残せば十分です。「Mac では通ったのに Windows で落ちた」は事故ではなく、このプロジェクトが欲しい情報そのものです。

止まる所

STOP 1 ／ 設定が止める

実在のサイトへ送信。的サーバ以外へ出る送信は、実行の前に弾かれます。例外的にそれが要るケースの条件は ONBOARDING.md §6 にあるので、読んでから拓也に一言ください。

STOP 2 ／ 設定が止める

master へ直接 push。拓也が並列で何本もセッションを走らせているので、直接入れると衝突します。必ず PR で。

STOP 3 ／ これだけは設定で止まらない

有料プランの契約——お金が動くこと。従量課金の API や外部サービスの購入も同じです。無料枠の中は自由。カード番号を求められたら、そこが無料枠の外——手を止めて拓也へ。

逆に、自分の PC の中の的サーバ（--form testbed）へは何件撃っても大丈夫です。外に出ないので。

説明書に「やらないでね」と書くのと、設定で禁止するのは強さが違う。だから STOP 1 と 2 は、Claude の自制ではなく deny に書いてあります。

3つのコマンド

/update

最新のコードを取ってきて、Python とテスト専用ブラウザをそろえ、テストまで回す。未 commit の変更があると安全側で止まる。

いつ: 作業を始めるとき、毎回

/verify

「テストが通る → 的サーバが立つ → 2件撃てる」の3段を確認して、結果を表で出す。落ちた段があれば Issue の下書きまで作る。

いつ: 環境をいじった後・何か変な時

/pr 3

Issue #3 を読み、枝を作り、実装し、テストを回し、PR を作る。Issue に完了条件が無いと、実装せず聞き返す。（#3 はあなたの最初の課題として、もう立ててあります。番号を変えれば他の Issue にも使えます）

いつ: Issue を1つやるとき

中身は .claude/skills/ に、ただのテキストで置いてあります。Claude が何をするつもりか全部そこに書いてある。読んで「ここ違うんじゃない」と思ったら、それも Issue にしてください。

あなた専用の種8行

貼るのは今日の「0–10分」、/update が通った直後です。これは repo の説明書ではなく、あなた自身の Claude Code の癖を決めるファイル。渡すのは種だけで、あとは自分で育てます。Mac の置き場は ~/.claude/CLAUDE.md（~ はホームフォルダ。無ければ作る）。

# 私の Claude Code の癖（種・自分で育てる）

- 読んでから動く。repo に CLAUDE.md があればその読み順に従う。読まずに実装を始めない
- 止まるのは「外に出るもの」（送信・公開・他人に届くもの）と「お金が動くもの」だけ。それ以外は聞かずにやって、終わってから報告する。可逆な操作は git で戻せるので承認は要らない
- 直すのは会話ではなくファイル。会話で直した癖は次のセッションで消える。私が「違う」と言ったら、このファイルか repo の docs に1行足す案をその場で出す
- 「テストしました」は出力（コマンドと結果）を貼ったときだけ有効。貼らずに緑と言わない
- 着手前に「これは何のN回目か」を自問し、2回目以上なら前例（docs・過去の PR・Issue）を先に引く
- 同じ失敗を2回したら、3回目は仕組みで防ぐ（チェック・スクリプト・skill）。人が気をつけるルールは増やさない
- ファイル・資産を作ったら、次の自分がどの言葉で辿るかを考えて索引に1行足す
- 長い作業の最後は「⚠️ 判断すること」の番号リストで締める。無くても「なし」と書く

言葉の補足だけ——「N回目」は同じ種類の作業を前にもやったか、「可逆」はやり直せるという意味です。貼る作業そのものは、Claude に「このテキストを ~/.claude/CLAUDE.md に足して」と言えば済みます。道具の数ではなく、この8行の癖のほうが本体です。

育て方は1つだけ

1行足すのは、Claude が間違えた直後だけ。先回りして書いた規則は守られず、失敗から生まれた規則だけが残ります。同じ行を2回足したくなったら、それは規則ではなく仕組み（skill や小さなチェック）の出番です。

増やしたくなったら、消すか移すかを先に決めてから足してください。8行しかないのは手抜きではなく、上限があるからです（理由は付録の④）。

ひとりで最初の1時間

0–10分——ターミナルで cd して bot-lab のフォルダへ移り、claude と打つ。「信頼しますか」「実行していいですか」は Yes で構いません（危ないものは聞かずに deny が弾きます）。/update が通ったら、上の種8行を貼り、ついでに「いま何を入れたか、3行で」と聞いてその3行を Issue #3 に貼っておく。

10–20分——/verify で3段の表が全部 OK になるのを見る。落ちたら、それが今日の成果です。

20–50分——/pr 3。Claude が読み・直し・PR を出すのを眺める。「なんでそうするの」と途中で聞いて構いません。

50–60分——GitHub の Pull requests タブに自分の行が1つ増えていれば完了。あとは何もしなくていい。増えていなければ、Claude の最後の出力を Issue #3 に貼る。

ターミナルも Claude Code も動かないときは、ブラウザから直接 Issue を立ててください。そこが最後の退路です。

詰まったら

Issue に貼るのは、LINE にスクショを送るより速い。ログをそのまま貼れて、拓也の側で打ち直しが要りません。Claude に「これを Issue にして」と言えば書いてくれます。

ひとつだけ逆のことを言います。環境まわりを Claude に全部やらせて、自分は見ていない——これはやらない方がいい。非エンジニアで Claude Code を業務に入れた人が、後からこう書いていました。

「環境構築だけは自分で一つずつ理解しながらやった方がよかった」

とはいえ、全部を理解してから進むのも無理です。だから1つだけ——/update の後に「いま何を入れたか、3行で」と聞いて、その3行を Issue #3 に貼っておく。後でおかしくなったとき、唯一の手がかりになります。

階段——この順で覚える

登り切った先が「Claude を拓也と同じ水準で使いこなす」状態で、その水準は道具の数ではなく種8行の癖でできています。全段ひとりで進みます（拓也は PR のレビューと Issue の返事だけ）。1段目の完了条件は Issue #3 に書いてあります。2段目で踏んだ罠を書き足す先は 事例集（docs/KNOWLEDGE.md）。3段目からが本業です——検知の目印で「これ数えてなくない？」を見つけて、完了条件つきの Issue を自分で立てるところ。

4段目で作る道具は自分の ~/.claude/ に置きます（repo には入れません。理由は下の付録①）。5段目で使うのは git worktree という、枝ごとに作業フォルダを分ける仕組みです。

付録: この作りの理由（今日は読まなくていい）

同じことをやった人たちが落ちた穴が3つあります。3つとも静かに壊れるのが共通点で、エラーが出ないので誰も気づきません。気をつけようがないものは、設計で避けるしかない。

穴①: 渡した仕掛けが、相手の OS で黙って壊れる

hook のファイルの場所の書き方によって "Failed to canonicalize script path" で落ちる、という Windows のバグ報告が上がりました。1か月後に bot が「30日動きが無い。まだ起きているならコメントを」と書き、それにこう返した人がいます。

"It's still occurring, and in macos."（まだ起きています。しかも macOS で）

直っていないし、Windows だけの話でもなかった。ところがその5週間後、bot はそのまま「無活動」として閉じました（2026年2月28日）。だからこの repo は、守らせたいことを hook ではなく deny に書いてあります。

出典: claude-code issue #12874／同 issue の macOS 報告コメント／類例 issue #6023

穴②: コピーして配った説明書は、半年で別物になる

同じ CLAUDE.md を3つの repo にコピーして配った結果が、こう書かれています。

"Three repos, three copy-pasted CLAUDE.md files, each edited independently. Six months later the conventions have diverged and nobody knows which one is right."（3つの repo に3つのコピー。半年後、規約はバラバラで、どれが正しいのか誰にも分からない）

コピーには継承のしくみがありません。片方を直しても、もう片方は直らない。しかも「ズレました」という通知はどこにも出ないので、気づくのは実害が出た後です。だから共有したいものは repo の中に1つだけ置いて、pull で届ける。あなたの手元に増えるコピーは種8行だけに絞ってあります。

出典: Sharing Claude Code configuration across a team — Jean-Guillaume Sio

穴③: 会話が長くなると、規則が守られなくなる

説明書に書いた規則がどれくらい持つかについて、Hacker News でこう書いた人がいます。

"Sure, for 4/5 interactions then will ignore those completely :)"（そうね、4〜5往復はね。そのあと完全に無視するけど :)）

正直に書くと、これは1人のコメントで、末尾に顔文字が付いた軽口です。追試も統計もなく、数字として使えるものではない。ただ「長い会話では規則が薄れる」という向き自体は、同じスレッドの他の実務者の話とも噛み合っています。

なので「4〜5往復で切ってください」とは言いません。代わりに1つの Issue を1つの会話で終えるという切り方にしてあります。Issue が終われば会話も終わるので、往復の数を自分で数えなくて済む。

出典: Hacker News のコメント

④ なぜ種は8行しかないのか

Claude Code を作っている Boris Cherny 本人が、この手の説明書について "Try to keep it under 1k tokens or so."（1,000トークン≒日本語で700〜1,000字）と書いています。そして肥大は雑な追記からではなく、正しい追記から起きます。ある開発チームの CLAUDE.md は 87行から378行に膨らみました。

「どの追記もその時は正しい判断で、間違って足した行は一行もない」

だから対策も「削る」ではなく「上限を超えた分は別のファイルへ引っ越させる」でした。

出典: Boris Cherny のコメント（Hacker News）／CLAUDE.md が肥大化する問題（TOKIUM 開発者ブログ）
