bot-lab ハンドブック

Claude Code は使える。でも他人と同じ repo（リポジトリ＝コードとその変更履歴を置いておく GitHub 上の場所。手元にあるのはその写しです）を、誰かと一緒に育てたことはない。——そこを埋めるための説明です。本編は10分、付録まで読んでも15分。打つコマンドは3つ、やってはいけないことは3つ、途中で聞き返されるのは2箇所。

何をやっているか あなたに頼むこと 覚えなくていい3つ 毎回の流れ 3つのコマンド 止まる所 種 最初の1時間 詰まったら ことば 階段 付録: この作りの理由

何をやっているか

この節で分かること: このプロジェクトが何を調べようとしているのか。

応募フォームを自分たちで1つ作ります。これを的サイトと呼びます。そこへ大量の応募を並列で撃ち、撃たれた側のログを自分で読んで「これは何人に見えるか」「どの信号で機械の仕業だと分かるか」を数える。

撃つ側と受ける側の両方を自分で持っているのがこのプロジェクトの形です。片方しか持っていないと、bot 検知が何を見ているのかは外から推測するしかありません。中を開けられるのは、自分で両方作ったときだけです。

あなたに頼むこと

この節で分かること: コードを書くこと以外に、あなたにしかできないことが3つあること。

  • Mac で動かす——拓也は Windows なので、Mac で壊れる所は拓也には原理的に見えません。あなたの環境が唯一の検出器です
  • 2台目のマシンになる——1台の中で並列を増やしても、どこかで頭打ちになります。別の回線・別の観測点が1つ増えることに意味がある
  • 「何を確かめたいか」を決める側に立つ——手を動かすのは Claude Code。あなたは問いを出す人です
エンジニアの経験は要りません。「動かなかった」は失敗ではなく成果です。それがこのプロジェクトがあなたから一番ほしい情報なので。

覚えなくていい3つ——repo を開けば勝手に効く

この節で分かること: 規則を暗記しなくていい理由。あなたの Claude が代わりに読みます。

拓也の環境設定は1ファイルも渡しません。あれは拓也の OS と拓也の運用に張り付いていて、持って行った先では動かないからです。共有したいものは全部 repo の中に置いてあって、git pull（後述の /update）で届きます。あなたの Claude Code が bot-lab のフォルダを開いた瞬間に、次の3つが効きます。

① CLAUDE.md——repo が Claude に読ませる説明書
フォルダを開くだけで読まれます。「テストはこう回す」「本番には勝手に送らない」など、Mac でも Windows でも守れる短い規則だけが書いてあります。あなたが読んで暗記するものではなく、あなたの Claude が読むものです。
② deny ルール——危ない操作は機械が拒否する
幹（master＝本物のコード）へ直接書き込む push、git add -A（手元の変更を中身も見ずに全部まとめて入れる操作）、本番（＝的サイトではない、実在する外部のサイト）への送信。この3つは Claude が実行しようとしても設定の段階で弾かれます。しかも deny は、あなたがフォルダを「信頼する」（＝Claude Code が初めてそのフォルダを開いたとき出る確認に Yes と答えること）より前から効きますし、あなたの手元の設定で緩めることもできません。禁止が常に許可より優先される、と公式 docs が明記しています。
③ skills——/ で始まる3つのコマンド
Claude Code で /pr 3 のように打つと、決まった手順を Claude が最後まで回します。手順書はあなたが読むものではなく、Claude が実行するものです。repo に入れてあれば、写しを持つ全員に自動で届きます。

出典: Claude Code 公式 docs — Settings（"deny and ask rules apply right away." ／ allow は "apply only after each teammate trusts the folder"）／同 — Permissions（"deny rules from any scope are evaluated before allow rules"）／同 — Skills（project skills は repo に入れればチーム全員に届く）

毎回の流れ

この節で分かること: 1件の作業が始まってから終わるまでの形と、その途中で機械が止めに入る2箇所。

やることは、Issue（GitHub 上の「やること・困りごと」1件。番号が付きます）を1つ選んで、PR（変更の提案）にするところまで。いつもこの輪を回します。

  1. 1bot-lab のフォルダで Claude Code を開く新しいセッション（＝Claude との1つの会話）を始める。前の Issue の会話は引きずらない
  2. 2/update を打つ最新にして、動かすのに要るものを揃える（中身は下の表）Claude が聞き返す①: まだ commit していない変更（ファイルは保存済みでも、履歴に刻んでいないもの）が手元に残っていると、上書きを避けてここで停止します。→ Claude に「変更を退避して続けて」と言えば進みます。そもそも「そんなコマンドは無い」と言われたら、Claude に「git pull してから /update」と言ってください（コマンド自体が repo から届くので、写しが古いと入っていません）
  3. 3Issue を1つ選ぶ1つだけ。2つ同時に手を出さない
  4. 4/pr 3 のように番号を打つIssue から PR まで Claude が一気に回す（中身は下の表）Claude が聞き返す②: Issue に「何ができたら完了か」が書かれていないと、実装に入らず質問を返します。→ 質問はその場の画面に出ます。答えられなければ、その質問を Issue #3 にコメントで貼って拓也に振ってください
  5. 5PR ができるWindows・Mac・Linux の3つでテストが自動で回ります。これを CI と呼びます
  6. 6拓也がレビューして merge（幹に取り込むこと）するPR が出た時点で拓也に通知が届きます。あなたから連絡は要りません

↻merge されたら、新しいセッションを開いて 1 に戻る

橙の番号＝そこで Claude が聞き返してくる止まったら、それは正常です

CI で「あなたの Mac では通ったのに Windows で落ちた」が出ることがあります。それは事故ではなく、このプロジェクトが欲しい情報そのものです。

1つの Issue につき、セッションは1つ。会話が長くなると Claude が最初の約束をだんだん守らなくなる、という報告があります（付録の穴③）。Issue が1つ終わったら、その会話は閉じて新しく開いてください。

3つのコマンド

この節で分かること: 打つものは3つだけで、それぞれ何をして、いつ打つのか。

打つもの何が起きるかいつ
/update最新のコードを取ってきて、Python の環境とテスト専用ブラウザ（Playwright という道具が使うもの。普段の Safari や Chrome とは別物）も揃え、テストまで回す。まだ commit していない変更が手元にあると安全側で止まる作業を始めるとき、毎回
/verify「テストが通る → 的サーバが立つ → 的サーバに2件撃てる」の3段を一発で確認して、結果を表で出す。落ちた段があれば Issue の下書きまで作る環境をいじった後・何か変な時
/pr 3Issue #3 を読み、枝を作り、実装し、テストを回し、PR を作って Issue にひとこと書く。Issue に完了条件が無いと、実装せず聞き返すIssue を1つやるとき

中身が気になったら .claude/skills/ に Markdown（見出し記号が付いただけの、ただのテキスト）で置いてあります。Claude が何をするつもりなのか、全部そこに書いてある。読んで「ここ違うんじゃない」と思ったら、それも Issue にしてください。

止まる所

この節で分かること: 「やってはいけない」は3つだけ。そのうち2つは設定が止め、残る1つはあなたが止める。

STOP 1 ／ 設定が止める
的サイト以外への本番送信。自分の PC の中に立てた的サーバ（--form testbed）には何件撃っても大丈夫です。外に出ていく送信は設定が拒否します。例外的にそれが要るケースの条件は ONBOARDING.md §6 にまとめてあるので、読んでから拓也に一言ください。
STOP 2 ／ これだけは設定で止まらない
お金が動くこと。有料プランの契約、従量課金の API（使った分だけ課金される外部サービスの窓口）、外部サービスの購入。ここは deny では止められません——契約はブラウザの中で起きるので、Claude Code の設定の外側だからです。支払い方法やクレジットカードを入れる画面が出たら、そこで手を止めて拓也に振ってください。無料枠の範囲で試すのは自由です——カード番号を求められた時点で、そこは無料枠の外です。
STOP 3 ／ 設定が止める
幹（master）への直接の push。拓也が並列で何本もセッションを走らせているので、直接入れると衝突します。必ず PR で。Claude が間違えて実行しようとしても deny が止めます。

STOP 1 と 3 は「Claude が判断して自制する」のではなく「設定が実行させない」形にしてあります。説明書に「やらないでね」と書くのと、設定で禁止するのは強さが違う。だから安全は文章ではなく deny に書いてあります。

あなたの ~/.claude/CLAUDE.md に貼る種

この節で分かること: repo の説明書とは別に、あなた自身の Claude の癖を決める8行があること。育て方は「間違えた直後に1行」。

これは repo の説明書ではなく、あなた自身の Claude Code の癖を決めるファイルです。渡すのは種だけで、あとは自分で育ててください。育てる前提のものだから、拓也のものとズレていい。

# 私の Claude Code の癖（種・自分で育てる）

- 読んでから動く。repo に CLAUDE.md があればその読み順に従う。読まずに実装を始めない
- 止まるのは「外に出るもの」（送信・公開・他人に届くもの）と「お金が動くもの」だけ。それ以外は聞かずにやって、終わってから報告する。可逆な操作は git で戻せるので承認は要らない
- 直すのは会話ではなくファイル。会話で直した癖は次のセッションで消える。私が「違う」と言ったら、このファイルか repo の docs に1行足す案をその場で出す
- 「テストしました」は出力（コマンドと結果）を貼ったときだけ有効。貼らずに緑と言わない
- 着手前に「これは何のN回目か」を自問し、2回目以上なら前例（docs・過去の PR・Issue）を先に引く
- 同じ失敗を2回したら、3回目は仕組みで防ぐ（チェック・スクリプト・skill）。人が気をつけるルールは増やさない
- ファイル・資産を作ったら、次の自分がどの言葉で辿るかを考えて索引に1行足す
- 長い作業の最後は「⚠️ 判断すること」の番号リストで締める。無くても「なし」と書く

目標は「Claude を拓也と同じ水準で使いこなす」ことで、その水準はこの8行の癖でできています。bot-lab 固有の約束（Issue の使い方・KNOWLEDGE の引き方）は repo の CLAUDE.md 側にあるので、ここには入っていません。だからこの種は、別の repo・別の仕事でもそのまま使えます。

育て方は1つだけ: 1行足すのは、Claude が間違えた直後だけ。先回りして書いた規則は守られず、失敗から生まれた規則だけが残ります。同じ行を2回足したくなったら、それは規則ではなく仕組み（skill や小さなチェック）の出番です。

置き場所は Mac なら ~/.claude/CLAUDE.md（~ はあなたのホームフォルダ。無ければ作る）。Claude Code に「このテキストを ~/.claude/CLAUDE.md に足して」と言えば済みます。

8行しかないのは手抜きではなく、上限の話です。Claude Code を作っている Boris Cherny 本人が、この手の説明書について "Try to keep it under 1k tokens or so."（1,000トークン≒日本語で700〜1,000字ほどに収めろ）と書いています。そして肥大は雑な追記からではなく、正しい追記から起きます。ある開発チームの CLAUDE.md は 87行から378行に膨らみましたが、書いた本人はこう振り返っています。

「どの追記もその時は正しい判断で、間違って足した行は一行もない」

だからそのチームの対策も「削る」ではなく「上限を超えた分は別のファイルへ引っ越させる」でした。あなたも増やしたくなったら、消すか移すかを先に決めてから足してください。

出典: Boris Cherny のコメント（Hacker News） — "Try to keep it under 1k tokens or so. We will show you a warning if it might be too big."／CLAUDE.md が肥大化する問題 — TOKIUM 開発者ブログ（87行→378行・対策は上限を超えた分の置き場を変えること）

ひとりで最初の1時間

この節で分かること: 今日ひとりでやる手順と、どこで止まってよいか。

誰かと画面を合わせる必要はありません。ひとりで、下の順に。詰まったら直そうとせず、そこで止めて Issue に貼ってください。それが唯一の逃げ道で、正しい逃げ道です。

0–10分ターミナルを開き、cd で bot-lab の写しがあるフォルダへ移動して claude と打つ。最初に「このフォルダを信頼しますか」と聞かれたら Yes。作業中に「これを実行していいですか」と聞かれたときも基本 Yes で構いません（本当に危ないものは、そもそも聞かずに deny が弾きます）。開いたら /update。「そんなコマンドは無い」と言われたら、Claude に「git pull してから /update」と言ってください。それでも駄目なら出た文字を Issue に貼って、今日はそこで終わりでいい。通ったら上の種を ~/.claude/CLAUDE.md に貼る（Claude に頼めば書いてくれます） 10–20分/verify。3段の表が全部 OK になるのを見る。落ちたら、それが今日の成果です。出力を丸ごと Issue に貼って、そこで終わりにしてください 20–50分/pr 3。Claude が Issue を読み、枝を作り、直し、テストを回し、PR を作るのを眺める。途中で「なんでそうするの」と聞いて構いません。答えられなければ、それも Issue のネタです 50–60分できたかどうかは、GitHub の bot-lab を開いて Pull requests タブを見れば分かります。自分の出した行が1つ増えていれば完了で、あとは何もしなくていい（拓也に通知が届きます）。増えていなければ、Claude の最後の出力を Issue #3 にコメントで貼ってください

ターミナルも Claude Code も動かないときは、GitHub の bot-lab を開いて Issues タブから直接 Issue を立ててください。そこが最後の退路です——手元が全部壊れていても、ブラウザさえあれば連絡はつきます。

1時間で PR まで行かなくても問題ありません。/verify が落ちて Issue が1本増えただけでも、輪は回っています。

詰まったら

この節で分かること: 詰まったときに自分で直そうとしなくていい理由と、代わりにやること。

  1. 環境まわり（Python・テスト用ブラウザ・gh の GitHub ログイン）で止まったら /verify。どの段で落ちたかが表で出ます。/ のコマンド自体が認識されないときは、Claude に「git pull してから」と言ってください
  2. その出力を全文、Issue に貼る。LINE にスクショを送るより速いです。ログをそのまま貼れて、拓也の側で打ち直しが要らない。Claude に「これを Issue にして」と言えば書いてくれます。テンプレートに「環境」「再現手順」の欄があります。貼る先は、/pr 3 の途中で止まったなら Issue #3 にコメント、/update や /verify で止まったなら新しい Issue
  3. そこで終わりにしていい。Mac 固有の失敗は、このプロジェクトがあなたに見つけてほしいものそのものです。黙って直してしまうと、何が壊れていたのかが残りません

ひとつだけ、逆のことを言います。環境まわりの手順を Claude に全部やらせて、自分は見ていない——これはやらない方がいい。非エンジニアの立場で Claude Code を業務に入れた人が、後からこう書いていました。

「環境構築だけは自分で一つずつ理解しながらやった方がよかった」

この人は環境構築を任せきりにしたことを失敗として振り返っています。とはいえ、全部を理解してから進むのは無理です。具体的にはこれだけやってください——/update が終わったら、Claude に「いま何を入れたか、3行で」と聞いて、返ってきた3行を Issue #3 のコメントに貼っておく。後でおかしくなったとき、それが唯一の手がかりになります。

出典: 非エンジニアが Claude Code を使ったら、開発プロセスが逆転し始めた ー実践・つまずき編（EARTHBRAIN・PdM）

ことば——これだけ分かれば会話が通じる

この節で分かること: 拓也や Claude が説明なしで使ってくる語の意味。

repo（リポジトリ）
コードと変更履歴を置いておく GitHub 上の場所。手元にあるのはその写し
clone
repo の写しを自分の PC に作ること。すでに済んでいます
Issue
GitHub 上の「やること・困りごと」1件。番号が付く（#3 など）
ブランチ（枝）
作業用の枝。master が幹で、変更はいったん枝で作る
commit
変更にひと区切り付けて履歴に刻むこと。Claude がやります
push
手元の変更を GitHub 側へ送ること
pull
逆に、GitHub 側の最新を手元の写しに取り込むこと。/update が最初にやるのがこれ
PR（プルリクエスト）
「この枝を幹に入れていい？」という提案。差分とテスト結果が見える
merge
PR を幹に入れること。拓也がやる
CI
PR を出すと自動で回るテスト。ここでは Windows・Mac・Linux の3つ
セッション
Claude Code との1つの会話。Issue 1件につき1つ
トークン
AI が文章を数えるときの単位。1,000トークンで日本語700〜1,000字ほど
venv
この repo 専用の Python の箱。source .venv/bin/activate で入る。/update が面倒を見る
gh
ターミナルから GitHub を操作する道具。ログイン済みです
grep
ファイルの中を語で探す命令。「この語がどこに書いてあるか」を一瞬で出す
的サーバ（testbed）
自分の PC の中に立てる、応募フォームの偽物。ここに撃つのは自由
dry-run
送る直前で止まるモード。内容は全部出るが送らない。既定はこっち
deny ルール
設定ファイルに書く禁止。Claude が何をしようとしても実行前に弾かれる
hook
特定の操作の前後で自動的に走る小さなプログラム。この repo では使っていません（付録の穴①）

階段——この順で覚える

この節で分かること: いま自分がどこにいて、次に何ができるようになればいいのか。

いきなり全部は要りません。1段ずつ。目標は⑤まで登って、拓也が bot-lab でやっているのと同じ形になること。全段ひとりで進めます（拓也は PR のレビューと Issue の返事だけ）。いまは1段目です。

  1. 使う——読んでから動く／止まるのは2か所だけ
    /update → /verify → /pr 3。完了条件は Issue #3 に書いてあります。手順は上の「最初の1時間」。上がった合図＝自分の PR が1本 merge される
  2. 直すのはファイル——Claude が間違えたら会話でなく docs に1行
    Issue #1（Mac の画面つきの起動）をひとりで通す。Mac でしか確かめられないので拓也は代われません。途中で踏んだ罠を docs/KNOWLEDGE.md に1本。合図＝KNOWLEDGE に自分の事例が1本ある
  3. 指示する——完了条件を自分で書く
    docs/detection-catalog.md（検知の軸のカタログ）から「これ測れてなくない？」を1つ選び、完了条件つきの Issue を自分で立てて /pr に渡す。合図＝自分が書いた完了条件だけで Claude が完走する。ここからが本業
  4. 仕組みにする——同じ失敗の3回目は機械に止めさせる
    自分の ~/.claude/ に skill か小さなチェックを1つ作る（repo には入れない。理由は付録の穴①）。合図＝~/.claude/CLAUDE.md の1行が消えて、代わりに道具が1つある
  5. 並列にする——1本のセッションで全部やらない
    git worktree で枝を2本切り、Issue を2つ同時に走らせる。自分は判断事項だけ吸い上げる。合図＝2本の PR が同じ日に出る

付録: この作りの理由（今日は読まなくていい）

この節で分かること: 同じことをやった人たちが落ちた穴が3つあり、上の作りはその3つを避けた結果だということ。

3つとも静かに壊れるのが共通点です。エラーが出ないので、壊れたことに誰も気づかない。気をつけようがないものは、設計で避けるしかありません。

穴①: 渡した仕掛けが、相手の OS で黙って壊れる

共有設定には hook——特定の操作の前後で自動的に走る小さなスクリプト——を仕込めます。「本番へ送る前に必ず確認を挟む」のような安全装置を書ける場所です。ところがこれは、書いた人の OS でしか動かないことがあります。

報告例が1つ。hook のファイルの場所の書き方によって "Failed to canonicalize script path" で落ちる、という Windows のバグ報告が上がりました。1か月後に bot が「30日動きが無い。まだ起きているならコメントを」と書き、それに対してこう返した人がいます。

"It's still occurring, and in macos."

直っていないし、Windows だけの話でもなかった。ところがその5週間後、bot はそのまま「無活動」として閉じました（2026年2月28日）。そして怖いのは、hook が壊れても作業自体は普通に進んでしまうことです。安全のための検査だけが静かに消える。

だからこの repo は、守らせたいことを hook ではなく deny に書いてあります。deny は設定ファイルの1行で、スクリプトを走らせません。走らないものは壊れようがない。

出典: claude-code issue #12874（"[BUG] Windows: Failed to canonicalize script path error with relative paths in hooks"・closed / not planned＝無活動による自動クローズ）／同 issue の macOS 報告コメント／類例 issue #6023（Windows で hook 内の環境変数が展開されない）

穴②: コピーして配った説明書は、半年で別物になる

同じ CLAUDE.md を3つの repo にコピーして配った結果が、こう書かれています。

"Three repos, three copy-pasted CLAUDE.md files, each edited independently. Six months later the conventions have diverged and nobody knows which one is right."

コピーには継承のしくみがありません。片方を直しても、もう片方は直らない。しかも「ズレました」という通知はどこにも出ないので、気づくのは食い違いが実害になった後です。

この repo が拓也の設定を1ファイルも渡さないのは、これが理由です。共有したいものは repo の中に1つだけ置いて、pull で届ける。あなたの手元に増えるコピーは「種」の8行だけに絞ってあります。

出典: Sharing Claude Code configuration across a team — Jean-Guillaume Sio（フリーランス開発者の実践記）。★同記事の処方は「共有 deny を git に入れる」「説明書には検査できる規則だけ書く」に加えて、共通部分を配布するスクリプトで揃える案も挙げています。この repo は逆に、配布そのものをやめる側に倒しました。

穴③: 会話が長くなると、規則が守られなくなる

Claude Code を扱った Hacker News のスレッドで、説明書に書いた規則がどれくらい持つかについて、こう書いた人がいます。

"Sure, for 4/5 interactions then will ignore those completely :)"

正直に書いておくと、これは1人のコメントで、しかも末尾に顔文字が付いた軽口です。追試も統計もありません。数字として使えるものではない。ただ「長い会話では規則がだんだん薄れる」という向き自体は、同じスレッドの他の実務者の話とも噛み合っています。

なので「4〜5往復で切ってください」とは言いません。代わりに1つの Issue を1つの会話で終えるという切り方にしてあります。Issue が終われば会話も終わるので、往復の数を自分で数えなくて済む。

出典: Hacker News のコメント（epolanski）
